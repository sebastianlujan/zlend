# ZLend Protocol Specification

## Overview

ZLend enables users to collateralize **ZCash shielded UTXOs** and borrow **ERC-20 tokens** on **Avalanche** through **Aave V3** — without revealing their ZCash address or balance on-chain. The protocol introduces **ZLend Units**, a novel primitive based on deterministic address derivation from ZCash's ZIP-32 standard.

---

## ZLend Units

A **ZLend Unit** is a deterministic address derived from ZCash's ZIP-32 hierarchical deterministic wallet specification. It binds a user's identity to a key pair that bridges ZCash and Avalanche.

### Key Derivation

```
ZLend = H(X, ZIP32) → vk, sk
```

| Symbol | Name | Description |
|--------|------|-------------|
| `X` | Identity input | User-specific entropy (e.g., seed phrase or identity commitment) |
| `ZIP32` | Derivation path | ZCash's HD key derivation standard (Sapling/Orchard) |
| `H` | Hash function | Cryptographic hash binding X to the ZIP-32 path |
| `vk` | Viewing key | Allows the protocol to verify UTXO ownership without spending authority |
| `sk` | Spending key | Retained client-side — authorizes collateral release and withdrawals |
| `d` | Deterministic address | The ZCash address generated by `createZLendAddress()` |

### Sub-Key Hierarchy

From `sk`, the Orchard protocol derives a full key tree:

```
sk (spending key) ── kept client-side, destroyed after FROST DKG
  ├→ ask = ToScalar(PRF_expand(sk, [0x06]))   ← Pallas scalar (PARALLEL from sk)
  ├→ nk  = ToBase(PRF_expand(sk, [0x07]))     ← Pallas base (PARALLEL from sk)
  └→ rivk = ToScalar(PRF_expand(sk, [0x08]))  ← Pallas scalar (PARALLEL from sk)

ask → ak = [ask] * G_Orchard                  ← public spend verification key

fvk = (ak, nk, rivk)                          ← COMPOSED from all three sub-keys

fvk → ivk  = Commit_ivk(rivk, ak, nk) mod r_P ← incoming viewing key (Sinsemilla)
fvk → ovk                                      ← outgoing viewing key
fvk → dk → d                                   ← diversifier key → deterministic address
```

**Note**: `ask`, `nk`, and `rivk` are **siblings** derived in parallel from `sk` — not a chain. The full viewing key `fvk` is *composed* from all three. Then `ivk`, `ovk`, and `dk` are derived from `fvk`. See [ZIP-224](https://zips.z.cash/zip-0224) for the full specification.

### Threshold Spending (FROST)

The spend authorizing key (`ask`) is split into a **(2, 3)** threshold scheme using **FROST** (Flexible Round-Optimized Schnorr Threshold signatures) with the `frost-rerandomized` RedPallas ciphersuite from `ZcashFoundation/frost`.

| Share Holder | Shares | Role |
|-------------|--------|------|
| User (browser) | Share 1 + Share 2 | Primary signer — can sign alone (2-of-3 met) |
| Relayer | Share 3 | Co-signer — cannot sign alone, but user + relayer = valid |
| Backup (cold storage) | Share 2 (copy) | Recovery — user share 1 + backup = valid |

**Why FROST over raw Shamir Secret Sharing:**

- FROST **never reconstructs** the full `ask` in memory — partial signatures are combined directly
- The resulting signature is **indistinguishable** from a standard Orchard RedPallas spend authorization
- The Zcash Foundation provides a production library: `ZcashFoundation/frost`
- Raw Shamir requires reconstructing `ask` to sign, creating a vulnerability window

**FROST signing (2 rounds):**

1. **Round 1 (Commit)**: Each participant generates a random nonce and publishes a commitment
2. **Round 2 (Sign)**: Each participant computes a partial signature using their share, the message, and all nonce commitments
3. **Combine**: The coordinator (user's browser) combines partial signatures into a valid RedPallas signature

### Properties

- **Deterministic**: Same inputs always produce the same ZLend Unit — no on-chain registration needed
- **Privacy-preserving**: The viewing key proves ownership without revealing the spending key
- **Cross-chain**: One derivation produces keys usable on both ZCash (UTXO verification) and Avalanche (proof submission)
- **Non-custodial**: The spending key never leaves the user's client
- **Threshold-secured**: `ask` is split via FROST — the full key is never materialized after DKG

## Protocol Flow

### Phase 0a — Address Creation

```
User → Browser (client-side): createZLendAddress()
Browser → User: deterministic address (d)
```

The user generates a ZLend-specific ZCash address derived from their identity via ZIP-32. This runs entirely client-side using `WebZjs` (ChainSafe/WebZjs, WASM-compiled Rust Orchard crate) — no node interaction required. This address will hold the shielded UTXOs used as collateral.

### Phase 0b — FROST Key Generation & Share Distribution

```
User → Browser: FROST DKG(ask) → share_1, share_2, share_3
User keeps: share_1, share_2 (browser encrypted storage)
User → Zcash shielded tx → Relayer z-address: share_3 (in encrypted memo)
User → age encrypt → cold storage: share_2 (backup copy)
```

1. **FROST DKG** — The browser runs FROST's Distributed Key Generation on `ask` (the spend authorizing key derived from `sk`). This produces 3 shares with a threshold of 2. The full `ask` is destroyed after DKG completes.
2. **Share distribution** — Share 3 is sent to the relayer via a Zcash shielded transaction. The share is first wrapped in a **NaCl `crypto_box`** (X25519 + XSalsa20-Poly1305) envelope encrypted to the relayer's public key, then embedded in the memo field. The memo itself is encrypted by Zcash's native note encryption (using the relayer's `ivk`). This provides **double encryption**: an inner NaCl layer (defense against `ovk` compromise) and an outer Zcash layer (standard Orchard privacy).
3. **Backup** — A copy of Share 2 is encrypted with `age` and stored offline for recovery.

#### Memo Field Format (ZLND Share Protocol)

The 512-byte Orchard memo field encodes a FROST share as follows:

```
Offset  Size  Field
------  ----  -----
0       4     Magic bytes: "ZLND" (0x5A4C4E44)
4       1     Version: 0x01
5       1     Share index (1–3)
6       1     Threshold t (e.g., 2)
7       1     Total shares n (e.g., 3)
8       N     NaCl crypto_box ciphertext (inner encryption layer):
                32 bytes: ephemeral X25519 public key
                32 bytes: encrypted FROST share (Pallas scalar) + 16 bytes MAC
                32 bytes: encrypted group public key commitment (ak) + 16 bytes MAC
              Total NaCl payload: ~128 bytes
136     376   Reserved (zero-padded)
```

The memo has two encryption layers: an inner NaCl `crypto_box` (X25519 + XSalsa20-Poly1305) providing defense-in-depth against `ovk` compromise, wrapped by Zcash's native note encryption (outer layer). The recipient first decrypts the outer layer with `ivk`, then decrypts the inner NaCl payload with their X25519 private key. This ensures that even if the sender's `ovk` is compromised, the FROST share remains protected.

### Phase 1 — Collateral Setup

```
User → Relayer: requestUTXOs
Relayer → User: nonce, vk, nullifier
User → ZLendContract: SupplyTransfer(amount, UTk)
User → ZLendContract: connectVk
```

1. **requestUTXOs** — The user requests UTXO data from the relayer, receiving a fresh nonce, the viewing key, and a nullifier (to prevent double-spending)
2. **SupplyTransfer** — The user submits a supply transaction with the amount and UTXO token reference (`UTk`)
3. **connectVk** — The viewing key is linked to the ZLendContract, enabling it to verify collateral existence

### Phase 2 — Borrow

```
User: generateProof(borrow)
User → ZLendContract: Borrow(proof, amount)
ZLendContract → Ultrahonk Verifier: verify(proof) → Success
ZLendContract → Aave V3: approval(addr, amount)
ZLendContract → Aave V3: supply(amount)
ZLendContract → Aave V3: borrow(amount)
ZLendContract → User: ERC20Transfer via ProtoSocolo
```

![Contract Interactions](assets/contract-interactions.png)

1. **generateProof** — Client-side Noir circuit generates an Ultrahonk proof asserting: "I own ZCash UTXOs worth ≥ X, here is my viewing key proof, and I have not already borrowed against these UTXOs"
2. **Borrow(proof, amount)** — Submitted to ZLendContract with the ZK proof and desired borrow amount
3. **Ultrahonk Verification** — On-chain verifier confirms the proof is valid
4. **Aave V3 Integration** — ZLendContract approves and supplies collateral to Aave V3, then borrows on behalf of the user
5. **ERC-20 Transfer** — Borrowed tokens are sent to the user via the ProtoSocolo ERC-20 contract

### Phase 3 — Repay

```
User → ZLendContract: Repay(amount)
```

Standard repayment flow through Aave V3. The user sends ERC-20 tokens back to repay their borrow position.

### Phase 4 — Withdraw

```
User: generateProof(repaying)
User → ZLendContract: withdrawProof(amount)
ZLendContract → Ultrahonk Verifier: verify(proof) → Success
ZLendContract → User: logs FinishPayment(zlend, amount, recipient, address)
```

1. **generateProof(repaying)** — Client generates a proof that the loan has been fully repaid and the collateral can be released
2. **withdrawProof** — Submitted with the ZK proof; Ultrahonk verifier confirms
3. **FinishPayment** — Event emitted with: `(zlend, amount, recipient, address)` — signals collateral release

## Mathematical Foundation

```
P = Σ(C, W)
```

Where:
- `P` — Protocol state (total position)
- `C` — Claims (active borrow positions backed by verified collateral)
- `W` — Withdrawals (collateral released after repayment)

This invariant ensures that at any point, the sum of all active claims and processed withdrawals accounts for every collateral unit in the system. A user can either **produce a claim** (borrow against collateral) or **deposit a shortfall** (repay to unlock collateral).

## Collateralization Model

| Parameter | Description |
|-----------|-------------|
| Collateral asset | ZCash (ZEC) shielded UTXOs |
| Borrow asset | ERC-20 tokens on Avalanche (via Aave V3) |
| Proof system | Ultrahonk (Noir/Barretenberg) |
| Collateral verification | ZK proof of UTXO ownership via viewing key |
| Liquidation trigger | Undercollateralization (ZEC value drops below threshold) |
| Nullifier | Prevents double-collateralization of the same UTXOs |

## Event Log

The protocol emits the following key event on successful withdrawal:

```solidity
event FinishPayment(
    address indexed zlend,    // ZLend unit address
    uint256 amount,           // Amount withdrawn
    address recipient,        // Recipient address on Avalanche
    address originAddress     // Associated collateral reference
);
```
