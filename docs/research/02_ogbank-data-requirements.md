# OGBank Data Requirements

> What data does OGBank generate, who stores it, and what needs to persist?

This document inventories every piece of data in the OGBank protocol lifecycle and classifies it by storage location, sensitivity, and lifecycle.

---

## Protocol Flow Recap

```
1. User requests account → Relayer creates ZCash escrow address
2. User receives: escrow address + viewing key (vk)
3. User deposits ZEC to escrow address from their ZCash wallet
4. User's browser uses vk to scan escrow → confirms deposit
5. User's browser generates ZK proof of deposit (Ultrahonk/Noir)
6. User sends tx to OGBankContract on Avalanche: proof + borrow amount
7. Contract verifies proof → borrows USDC from Aave V3 → sends to user
8. User repays USDC on Avalanche over time
9. User generates repayment proof
10. User sends repayment proof to OGBankContract
11. Contract verifies → signals relayer
12. Relayer sends ZEC back to user's origin address
```

Key trust model: **Relayer holds the ZCash spending key** (escrow custody). **User holds the viewing key** (read-only access + proof generation).

## Data Inventory by Phase

### Phase 0 — Account Creation

| Data | Generated by | Stored by | Format | Lifecycle |
|------|-------------|-----------|--------|-----------|
| ZCash escrow address | Relayer (ZIP-32 derivation) | Browser, Relayer | ZCash Sapling address (`zs1...`) | Permanent per account |
| Viewing key (vk) | Relayer (derived from spending key) | Browser | `(ak, nk, ovk, dk)` — 4 components, ~128 bytes total | Permanent per account |
| Spending key (sk) | Relayer (ZIP-32 derivation) | **Relayer only** | ZCash spending key | Permanent, never shared |
| User's Avalanche address | User's wallet | Browser (MetaMask) | Ethereum address (`0x...`) | Pre-existing |
| Account mapping | Relayer | Relayer DB | `{ avalancheAddr → escrowAddr, vk }` | Permanent |

**What the browser must persist after this phase:**
- Viewing key (vk)
- Escrow address
- Association with the user's Avalanche wallet

### Phase 1 — Deposit

| Data | Generated by | Stored by | Format | Lifecycle |
|------|-------------|-----------|--------|-----------|
| ZEC deposit transaction | User (from their ZCash wallet) | ZCash blockchain | Shielded UTXO | Permanent on-chain |
| UTXO at escrow address | ZCash network | ZCash blockchain | Shielded note | Until spent |
| Deposit confirmation | Browser (via vk scanning) | Browser cache | `{ amount, txid, confirmations }` | Session, refreshable |

**What the browser must persist:**
- Nothing new — the viewing key already allows re-scanning the deposit at any time

### Phase 2 — Borrow

| Data | Generated by | Stored by | Format | Lifecycle |
|------|-------------|-----------|--------|-----------|
| UTXO scan result | Browser (using vk) | Browser memory | `{ balance, utxos[] }` | Ephemeral, re-scannable |
| User secret | Browser (derived or random) | Browser (secure) | 32 bytes | Permanent per account |
| Borrow nonce | Browser | Browser + Relayer | uint256, monotonic | Incremented per borrow |
| State root | OGBankContract | On-chain | bytes32 | Sliding window (30 roots) |
| Borrow nullifier | Browser (computed) | On-chain after submission | `H(user_secret, borrow_nonce, state_root)` — bytes32 | Permanent once submitted |
| ZK borrow proof | Browser (Noir/Ultrahonk) | Transient | Ultrahonk proof (~600-1000 bytes) | Discarded after submission |
| Borrow tx receipt | Avalanche | On-chain logs | Transaction hash + events | Permanent on-chain |
| USDC balance | Aave V3 → ProtoSocolo | On-chain (ERC-20 state) | uint256 | Until repaid |

**Proof inputs (private — never stored on-chain):**

| Input | Source | Sensitivity |
|-------|--------|-------------|
| `user_secret` | Browser-generated | CRITICAL — allows nullifier derivation |
| `borrow_nonce` | Browser counter | HIGH — must be monotonic |
| `viewing_key` | From Phase 0 | HIGH — allows balance scanning |
| `utxo_amount` | From vk scan | MEDIUM — actual deposit amount |
| `merkle_path` | ZCash blockchain | LOW — proves UTXO inclusion |

**Proof inputs (public — visible on-chain):**

| Input | Purpose |
|-------|---------|
| `borrow_nullifier` | Unique cycle identifier |
| `borrow_amount` | How much USDC to borrow |
| `state_root` | Temporal binding |

**What the browser must persist after this phase:**
- User secret (CRITICAL — needed for withdrawal proof)
- Current borrow nonce (must track across sessions)
- Borrow nullifier (to reference in withdrawal)
- Borrow amount (for display/tracking)

### Phase 3 — Repay

| Data | Generated by | Stored by | Format | Lifecycle |
|------|-------------|-----------|--------|-----------|
| USDC repayment tx | User | On-chain | ERC-20 transfer | Permanent |
| Remaining debt | Aave V3 | On-chain | uint256 | Decreases to 0 |

**What the browser must persist:** Nothing new — repayment is a standard ERC-20 transfer on Avalanche.

### Phase 4 — Claim (Withdraw)

| Data | Generated by | Stored by | Format | Lifecycle |
|------|-------------|-----------|--------|-----------|
| ZK repayment proof | Browser (Noir/Ultrahonk) | Transient | Ultrahonk proof | Discarded after submission |
| Consumed nullifier | OGBankContract | On-chain | `consumedNullifiers[nullifier] = true` | Permanent |
| FinishPayment event | OGBankContract | On-chain logs | `(ogbank, amount, recipient, originAddress)` | Permanent |
| ZEC return tx | Relayer | ZCash blockchain | Shielded transaction | Permanent |

**Repayment proof inputs (private):**

| Input | Source |
|-------|--------|
| `user_secret` | Same as borrow phase |
| `borrow_nonce` | Same as borrow phase |
| `merkle_path` | Contract state proof |

**Repayment proof inputs (public):**

| Input | Purpose |
|-------|---------|
| `borrow_nullifier` | Identifies which borrow cycle |
| `state_root` | Current contract state |
| `amount` | Amount being withdrawn |

## Client-Side State Summary

Everything the browser needs to persist across sessions:

| Data | Sensitivity | Size | When Created | When Consumed |
|------|------------|------|-------------|---------------|
| **Viewing key (vk)** | HIGH | ~128 bytes | Account creation | Never (reused every session) |
| **Escrow address** | MEDIUM | ~70 bytes | Account creation | Never (reused) |
| **User secret** | CRITICAL | 32 bytes | First borrow | Every proof generation |
| **Borrow nonce** | HIGH | 8 bytes | First borrow | Incremented each cycle |
| **Active borrow nullifiers** | MEDIUM | 32 bytes each | Each borrow | Each claim |
| **Borrow history** | LOW | Variable | Each borrow | Display only |
| **Event polling state** | LOW | ~16 bytes | First event scan | Updated continuously |
| **User preferences** | LOW | Variable | User settings | Persistent |

### Total persistent state per account: ~300 bytes minimum + history

## Relayer-Side State

| Data | Sensitivity | Purpose |
|------|------------|---------|
| Spending key (sk) per escrow | CRITICAL | Move ZEC from escrow addresses |
| Escrow address → Avalanche address mapping | HIGH | Route borrowed tokens and return ZEC |
| Viewing key registry | HIGH | May store vk → address associations |
| Transaction logs | MEDIUM | Audit trail, debugging |
| Nonce sync state | MEDIUM | Ensure nonce consistency with client |

## On-Chain State (Avalanche)

| Mapping | Contract | Purpose |
|---------|----------|---------|
| `viewingKeyRegistry[address => bytes]` | OGBankContract | Links user to their vk |
| `borrowNullifiers[bytes32 => bool]` | OGBankContract | Active borrow cycles |
| `consumedNullifiers[bytes32 => bool]` | OGBankContract | Completed cycles |
| `validStateRoots[bytes32 => bool]` | OGBankContract | 30-root sliding window |
| `positions[address => Position]` | OGBankContract | Collateral/debt tracking |
| Aave V3 supply/debt positions | Aave Pool | Protocol-level collateral |
| ProtoSocolo ERC-20 balances | ProtoSocolo | Borrowed token balances |

## Data Sensitivity Classification

| Level | Data | Risk if Compromised | Storage Requirement |
|-------|------|---------------------|---------------------|
| **CRITICAL** | User secret, spending key (sk) | Collateral theft, unauthorized withdrawal | Encrypted storage, never transmitted |
| **HIGH** | Viewing key (vk), borrow nonce | Privacy loss (attacker can scan balances), nonce manipulation | Secure client storage |
| **MEDIUM** | Escrow address, nullifiers, UTXO cache | Transaction pattern analysis | Standard persistence |
| **LOW** | Proof data (post-submission), event logs | Public knowledge after on-chain | Can be transient |

---

## Key Insight: What Kohaku Would Store

If Kohaku serves as the client-side state manager for OGBank, it needs to handle:

1. **Viewing key persistence** — Via `Host.storage` (key-value). Ideally `SecretStorage` for encryption at rest.
2. **User secret** — CRITICAL. Needs `SecretStorage` or equivalent encrypted persistence.
3. **Borrow nonce tracking** — Simple counter in `Host.storage`.
4. **Active nullifiers** — Array of bytes32 in `Host.storage`.
5. **UTXO scanning** — Not storage per se, but requires `Host.network` for ZCash RPC calls.
6. **Event polling** — Via `Host.provider` (Avalanche RPC) for contract events.
7. **Proof generation** — Not a storage concern, but needs circuit artifacts via `Host.network`.

What Kohaku does NOT need to handle:
- Spending key (stays with relayer)
- On-chain state (queried from Avalanche)
- Aave V3 state (queried from Aave)
- ZCash blockchain state (queried from ZCash RPC)
